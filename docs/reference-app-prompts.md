# Reference-application prompts

Use these after committing and updating the project skills. Each prompt creates a separate application repository; it does not add an application to a skill repository. These are extended versions of the regular plan-then-build prompts in the [planning guide](project-planning.md).

Install the corresponding skill, create an empty folder, initialize Git, and open it in Codex. Paste the planning prompt first, review PROJECT_PLAN.md, then use the implementation prompt. Both examples are local-only so no cloud resources need to be created. An operator may later opt into read-only live OCI testing using their own configuration.

## Python: Object Storage inventory CLI

### Plan

> Help me plan an OCI Python reference application before building it. The users are cloud operators who need a read-only inventory of Object Storage buckets in one explicitly selected compartment and region. Use the `oci-python-project` skill and its CLI format. Choose local-only operation; do not generate container or deployment resources. Use local OCI config-file authentication for live access, with an injectable OCI adapter and an explicit offline demo mode using synthetic data. The CLI should list bucket names and creation times in a readable table or JSON, follow pagination, and handle empty results, invalid configuration, denied access, and service errors with useful messages and exit codes. Never list or download object contents or modify resources. Keep it small: no UI, database, scheduler, or extra frameworks. Create PROJECT_PLAN.md with scope, command examples, authentication/configuration, least-privilege IAM requirements, test strategy, and acceptance checks. Record the skill source and Git revision if discoverable. Ask only for unresolved decisions that change the implementation, and stop before building so I can review the plan. Do not request real credentials or OCIDs in chat or tracked files.

### Build, test, and commit

> Read the approved PROJECT_PLAN.md and implement the Python reference application using `oci-python-project`. Preserve the plan's scope. Replace every starter placeholder, commit uv.lock, copy in the structural checker, and provide the standard run/ interface and concise operational documentation. Apply the skill's environment-sync workflow: derive supported inputs from code and requirements, preserve local values, keep optional overrides concise, remove proven-defunct inputs only from the example while retaining their local values as inactive DEFUNCT comments, and test operation-specific configuration preflight. Do not require live OCI settings in offline demo mode. Make offline demo mode runnable without OCI credentials and test it through the actual CLI entrypoint. Add meaningful offline tests for pagination, empty results, output formats, argument/config errors, denied access, and service failures. Mock the adapter in unit tests and verify the real SDK adapter's call/response mapping with synthetic fixtures. Include an opt-in live smoke-test procedure that performs only the documented read-only bucket listing; do not run it without my explicit instruction and local configuration. Run setup, lint, tests, package build/install verification, and the structural checker; fix failures. Add CI that installs from the lockfile and runs offline checks. Record commands, results, remaining limitations, and the skill revision in docs/verification.md. Explain any necessary standard exception. Review git diff and staged files for credentials, real resource identifiers, generated artifacts, and unrelated changes. Commit the completed application locally with a descriptive message. Do not push, create a remote repository, deploy, or transfer ownership. Report the commit and exact local commands for demo mode and separately configured read-only live access.
